# Nouvelle philosophie

Le système ne doit plus demander le capital à chaque trade.

Le capital est désormais considéré comme une donnée relativement stable.

Nous allons donc mettre en place un **Weekly Capital Cache** (TTL de 7 jours).

## Fonctionnement attendu

Une fois par semaine (ou lorsque le capital est expiré) :

* le système demande le capital à l'utilisateur ;
* le capital est enregistré en base ;
* le capital est chargé dans un cache mémoire ;
* ce capital devient la référence pendant toute sa durée de validité.

Ainsi, pendant toute la semaine :

aucun formulaire de capital ne doit être affiché si le capital est déjà disponible.

# Suppression d'une étape

Supprimer totalement l'étape :

```
Confirmer le trade
```

Elle n'apporte aucune valeur.

Dorénavant :

si l'utilisateur ouvre le trade,

cela signifie qu'il décide de le prendre.

Le système considère donc automatiquement le trade comme accepté.

Le calcul est lancé immédiatement.

L'enregistrement est effectué immédiatement.

Aucune confirmation supplémentaire.

---

# Le calcul

Attention.

Le capital provient du Weekly Capital Cache.

En revanche :

les paramètres techniques proviennent TOUJOURS du trade actif.

Exemple :

Trade A

```
Entry

3345

SL

3355

TP1

3330
```

Trade B

```
Entry

3320

SL

3310

TP1

3338
```

Le système ne doit jamais réutiliser :

* le SL précédent ;
* le TP précédent ;
* l'Entry précédente.

À chaque nouveau trade :

le calcul doit être effectué avec :

```
capital_cache_utilisateur

+

entry_du_trade_actif

+

sl_du_trade_actif

+

tp_du_trade_actif
```

Ainsi :

le lot,

la perte,

les gains,

restent toujours cohérents avec le trade envoyé.

---

# Gestion du cache

Créer un composant spécialisé :

WeeklyCapitalCache

Chaque entrée contient :

```
user_id

capital

version

updated_at

expire_at
```

Règles :

* lecture RAM prioritaire ;
* si absent → lecture SQL ;
* si trouvé → copie immédiate dans le cache ;
* si absent → formulaire utilisateur ;
* expiration automatique après 7 jours.

Le cache doit permettre de servir immédiatement plusieurs dizaines de milliers de calculs sans accès SQL.

---

# Campagne hebdomadaire

Le week-end,

une tâche planifiée lance automatiquement une campagne de mise à jour des capitaux.

Elle ne doit jamais envoyer le formulaire à tous les utilisateurs simultanément.

Le traitement doit être progressif.

Exemple :

```
300 utilisateurs

↓

pause

↓

300 utilisateurs

↓

pause

↓

300 utilisateurs

...

jusqu'à la fin
```

Ainsi la charge reste constante.

---

# Gestion des nouveaux utilisateurs

Si un utilisateur rejoint en milieu de semaine :

ne pas attendre le prochain week-end.

Lors de son premier clic :

```
RAM

↓

SQL

↓

si absent

↓

demande du capital

↓

mise en cache
```

Il entre ensuite dans le cycle normal.

---

# Une seule session Gold active

Avant chaque broadcast :

vérifier qu'aucune session Gold n'est encore active.

Si une session existe :

* terminer proprement la précédente ;
* attendre la fin des écritures critiques ;
* vider les buffers ;
* vider les workers ;
* nettoyer les callbacks expirés ;
* nettoyer la RAM ;
* recharger complètement les structures mémoire.

Ensuite seulement :

créer la nouvelle session.

Deux sessions Gold ne doivent jamais coexister.

---

# Nettoyage après chaque trade

À la fermeture d'une session :

effectuer automatiquement :

* flush des buffers ;
* synchronisation SQL ;
* vérification de cohérence ;
* suppression des états utilisateurs ;
* suppression des callbacks expirés ;
* nettoyage mémoire.

Le système doit repartir dans un état propre.

```
↓

↓

TP

↓

↓

```

Le système ne doit jamais mélanger deux sessions.

Toutes les validations doivent vérifier :

```
session_id

version

trade_id

timestamp
```

avant tout traitement.

# Vérifications automatiques

À la fin de chaque simulation vérifier automatiquement :

* aucun utilisateur ne reçoit un mauvais trade ;
* aucun utilisateur ne reçoit un ancien SL ;
* aucun utilisateur ne reçoit un ancien TP ;
* chaque lot correspond bien au trade actif ;
* chaque calcul correspond bien au capital présent dans le cache ;
* aucun utilisateur ne reçoit deux confirmations ;
* aucune fuite mémoire ;
* aucun buffer bloqué ;
* aucune incohérence RAM / SQL ;
* aucune session mélangée ;
* aucune race condition détectée.
